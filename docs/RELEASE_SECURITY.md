# 公开发布安全、加密与完整性

## 威胁模型

主要风险包括临床数据或自由文本误提交、内部路径/主机泄漏、凭据和私钥进入历史、模型权重意外公开、大文件或归档绕过人工检查，以及发布文件与审核版本不一致。

## 默认拒绝策略

- 只从明确白名单复制代码、模板、合成示例和文档。
- 拒绝临床/图像/模型/归档/表格数据常见扩展名。
- 拒绝大于5 MiB的文件。
- 拒绝模型、adapter、优化器、NumPy矩阵、常见权重容器和Git LFS指针；权重不得通过GitHub Release、Issue附件或外部下载链接旁路发布。
- 扫描私钥头、GitHub/云凭据、手机号、身份证号、病历标识、用户目录、私有挂载和内部端点模式。
- 拒绝包含字面反斜杠的 Git 路径，避免 Linux 可提交但 Windows 无法检出。
- 解析JSON、编译Python并运行关键单元测试。
- 使用 `tools/privacy_audit_history.py` 扫描所有可达历史 blob，避免敏感内容只从当前版本删除却仍留在历史中。

## 为什么不上传“加密后的临床包”

公共Git历史和镜像长期存在。如果密钥未来泄漏、密码强度不足或加密实现有误，密文仍可能被恢复。敏感数据应留在机构批准的访问控制环境中，而不是通过加密来取得上传公共仓库的资格。

提交元数据同样属于发布面：author、committer、邮箱和提交消息必须接受审计。本项目的公开默认分支只允许维护者的GitHub noreply身份，不接受`Co-authored-by`；这既避免个人邮箱泄漏，也保证贡献者统计不被本地工具或机器人污染。

如机构要求长期归档，应在Git之外使用批准的加密存储、独立密钥管理、最小权限和访问审计。仓库只保存非敏感的归档标识或机构内部登记号，不保存密文或密钥。

`tools/create_private_archive.ps1` 可用于经授权的仓库外离线归档：由 7-Zip 交互式获取口令、启用 AES-256 与文件名加密、完成解密测试并生成 SHA-256 sidecar。它不能替代数据所有者批准、访问控制或密钥管理。

## 哈希的作用

SHA-256用于检测文件是否改变：同一字节序列应得到同一哈希。它不加密文件、不隐藏内容、不证明匿名化，也不证明来源可信；可信发布仍需要受控生成流程和提交签名/平台身份。

`RELEASE_SHA256.txt`覆盖全部Git跟踪文件，但排除清单自身，避免自引用。CI重新生成清单并要求工作树无差异。

本项目不使用Git LFS。LFS只把大文件内容移到另一对象存储，仓库仍公开可定位对象的指针，不能把私有权重变成可公开资产。

## 发现泄漏时

1. 立即将仓库设为私有并撤销泄漏凭据；
2. 通过批准的私密渠道通知机构安全/隐私联系人；
3. 从完整Git历史中移除敏感内容，而不只是删除最新文件；
4. 检查fork、缓存和镜像，并在完成评估前按已披露处理。
